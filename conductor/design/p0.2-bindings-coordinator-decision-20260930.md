# P0.2 minimum ED binding decision

**Status:** accepted as an ED input-schema target by the coordinator after
separate E0 and C0 agent reviews. It defines synthetic model inputs for a
headless Macro scenario. It does not accept clinical values, a Kairos public
API, observed occupancy, or a completed Rust runtime.

## Identity and capacity

- A scenario declares unique, nonempty `zone_id`, `location_id`,
  `task_class_id`, `staff_role_id`, and `resource_id` values. Every location
  belongs to one declared zone. A resource ID names one allocatable bucket
  bound to one declared location and its zone. A `pool_group_id` may group
  several location buckets, but the group itself is never an additional
  allocatable resource. This reconciles E0's multi-location pool need with
  C0's single-location resource identity.
- Each resource bucket declares its class, capacity status, physical count,
  effective open and staffed counts, and capability/eligibility. Known counts
  are nonnegative and satisfy staffed <= open <= physical; unknown is null,
  never zero or allocatable. A required task with unresolved capacity fails
  validation or run setup rather than receiving a default. An unused optional
  bucket may remain unknown.
- The existing department `capacity` object is an aggregate/reporting
  constraint for treatment spaces. It is not another allocatable pool. Where
  the treatment-space buckets are declared complete and known, their initial
  physical/open/staffed counts must equal the corresponding known aggregate
  counts. If completeness or any relevant count is unknown, no equality is
  inferred; a profile requiring those resources stays unresolved. Other
  resource classes are not summed into treatment-space capacity.
- Availability changes use half-open logical intervals with a declared
  cause/basis. Their composition and the effect of a capacity decrease on
  active allocations belong to E0/Q execution contracts; until defined, the
  MVP schema may validate static initial capacity but must reject unsupported
  overlapping or in-flight changes at run setup. No observed occupancy or
  assignment event is allowed to silently alter configured capacity.

## Staff and eligibility

- A staff role is synthetic, not a person record. Counts declare their basis
  (`employed`, `rostered`, `present`, or `task_eligible`) and reference time or
  interval. A present/eligible count is not inferred from a rostered count or
  observed task starts. The generic MVP needs known effective present
  capacity for every required task, while optional unused roles may be unknown.
- Eligibility is an explicit relation among staff role, task class and zone,
  with an optional location in that zone. Omitted location means zone-wide
  eligibility; omitted role/task/zone entries confer no eligibility. Every
  reference resolves exactly. A role with several eligibility rows is still
  one capacity source, not duplicated staff.
- For the E2 baseline, one synthetic dispatch agent represents one effective
  concurrent present role slot, with a stable run-local ID and at most one
  active task at a time. This is an E0 execution mapping to verify, not a
  physical staff identity or a claim that one person cannot hold several
  real-world skills. Cross-role agent composition waits for a separate review.

## Observation and spatial boundary

Configured resource and staff capacity, eligibility, and availability live in
ED scenario data. Observed occupancy, reservation, staff assignment and
physical movement belong in C0/C1 trace records with occurrence and recorded
times, source keys and observed/derived/unknown provenance. An observed
over-capacity episode is reported as a mismatch; the validator never raises
declared capacity to fit it.

Macro mode consumes named zone/location bindings as categorical placement and
eligibility. It needs no route graph, coordinates, CAD or renderer. Micro mode
may add graph and travel inputs through its own reviewed contract. A missing
route in Macro mode is valid.

## Implementation and acceptance checks

The next schema revision must add resource buckets, task classes, staff roles
and eligibility while preserving the existing synthetic capacity/location
examples through an explicit migration. Semantic validation must reject
duplicate/empty IDs, bad references, zone/location mismatch, count ordering,
unknown required capacity, aggregate/bucket double counting, and a location
specific task with no eligible role/resource. Add negative fixtures for each.
The current v2 validator proves only capacity ordering and zone/route reference
checks. This decision becomes a P0.2 accepted input interface only after the
new schema, validator, examples and independent review pass; the P0.2 parent
remains open meanwhile.
