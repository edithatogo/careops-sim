# P0.2 E0 minimal resource and staff-role bindings

**Status:** proposed E0 input for independent review; not accepted, frozen, or an
implementation/API specification.

## Proposed minimum contract

The scenario declares stable, non-empty IDs for zones and named locations. Each
location references exactly one declared zone. IDs identify model concepts across
profiles and runs; display names may change and are not references.

Each logical resource pool has a unique `resource_id`, a declared capacity value
or explicit unknown status, and one binding to a declared `zone_id` and
`location_id`. The location's zone must equal the binding's zone. A pool ID is a
simulation resource concept (for example, a treatment-space pool), not a real
asset or patient/staff record. Multiple separately modeled pools use separate
IDs. Capacity counts are model inputs and do not assert observed or recommended
hospital capacity.

Each `staff_role_id` identifies a synthetic role/skill class, not a person. Role
staffing is expressed as counts and time-varying availability by that role;
individual staff identities or source-system records are outside this contract.
Each role binding names a declared zone and may name a location in that same
zone. A role may have multiple explicit bindings. Eligibility is an explicit
relation from role to declared task/activity classes at the bound zone and,
when present, location. An omitted task or location is not inferred as eligible.
At dispatch, only available simulated capacity for a role eligible for the
task's zone/location can perform it. E0 must define how role counts and
eligibility become synthetic agent capacity; this proposal does not define a
staff-person generation algorithm.

For the Macro MVP, zone/location bindings are categorical placement and
eligibility constraints. They require no route graph, distance, movement, CAD,
floor-plan geometry, or visual representation. If a scenario enables Micro
movement, route endpoints must reference declared locations and spatial units
must follow the separately reviewed spatial contract. Macro configurations
need not provide routes.

Unknown capacity remains distinct from zero: unknown values cannot be consumed
as available capacity. A profile that needs a resource or eligible role with
unknown capacity is invalid for that run until the input is resolved. Zero is
valid only as an explicit known value and makes that pool unavailable.

## Invalid or unresolved references

- Duplicate or empty IDs within a zone, location, resource-pool, or staff-role
  namespace; references are exact IDs, never display names.
- A location with an undeclared zone; a resource or role binding with an
  undeclared zone/location; or a binding whose location belongs to a different
  zone.
- An eligibility entry with an undeclared role, zone, location, or task class;
  a location-specific eligibility whose location is outside its declared zone.
- A resource pool assigned ambiguously to multiple locations, a negative
  capacity, or a known/unknown status inconsistent with its value. Unknown is
  not zero and cannot authorize allocation.
- A Micro route with an undeclared endpoint. Missing routes alone are not an
  error for Macro MVP.
- A required task with no eligible, known, available role/resource: validation
  or run must report the unmet binding explicitly; it must not invent a default
  role, resource, zone, location, route, or capacity.

Task/activity vocabulary, capacity granularity, shared-resource semantics,
whether every role binding requires a location, and the exact unknown-capacity
failure point remain E0/C0 decisions. No clinical task rule or default is
established here.

## Ownership and review gate

The parent ED/E0 owner owns the ED configuration shape, IDs, validation and
mapping into Kairos. Kairos Track 03 owns execution semantics; this proposal
does not change its API. E0 and C0 owners must review the binding shape and
eligibility semantics independently. The P0.2 coordinator must reconcile their
dispositions, align affected parameter-matrix rows and schemas, and add
reference/negative fixtures before acceptance. A separate review is required
before this proposal can be accepted or used to dispatch implementation.
