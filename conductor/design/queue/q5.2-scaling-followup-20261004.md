## Proposed bounded architecture
Keep public components, scheduler, tie ordering, lifetime caps and ownedcontext API unchanged. No new dependency or backend. Stage only the causal resource closure and touched request/progress records; commit only owned deltas after aggregatepreflight.

1. Pure queue overlay: borrowed authoritative BTreeSet plus added/removed keysets. contains/insert/remove are logarithmic; sorted iteration merges base and changes without fullclone. Original component remains BTreeSet. Clone overlay copies only deltas for boundaryrollback. Preflight exports ownedkeydeltas; commit applies removals/additions to the unchanged base after all checks. Unit tests compare against independent BTreeSet operationsequences, including clone/rollback/reinsert/rekey/extrema/order and unchangedbase.
2. Typed record overlay: borrowed registry with lazy cloned values only on get_mut; reads fall through to authoritative records. Clone only changedrecords to preserve boundary versus explicit rollback. Export owned writes; avoid collecting allrequests/progress. Maintenance scans for despawn/remove may remain readonly and explicitly measured.
3. Causal resource closure: submit/deadline/cancel/reprio/completion/release target theirrequest resource; capacity/remove targetone; despawn targets allowner nonterminal resources. Include all due work and eligible queue members of those resources. Preemption/regrant can mutate multiple participants in thatclosure. No unrelated resource cloning/committing.
4. Deadline lookup and reconciliation: owned internal ordered waitingdeadline index maintained atomically on every queue lifecycle path, including initial admission, deadline-clear, grant, cancel, timeout, suspend/requeue and actorcleanup. Query only dueentries. Before materializing waiters, inspect holders; if no timed/preemptible/noncompleted positive-remaining holder exists, skip replacement. Preserve mixed-mode queue and hold completion/deadline tie semantics. Cache/index is internal, not a new public authority or fixture.

## Independent architecture review disposition
Read-only review of the combined production code confirmed that overlays and causal closure alone cannot satisfy the unchanged 100,000-request gate. The waiting-deadline scan remains linear per event; eligible replacement materializes and sorts all waiters. Coordinator agrees: deadline lookup and scalable replacement are required remediation leaves, not optional polish. This remains a design for the next bounded source work, not permission for a benchmark worker to change the runtime.

Freeze these additional contracts before dispatch:
- Queue delta export preflights base-key membership and duplicate insertions before any authoritative mutation. Ordered iteration must equal the independent BTreeSet baseline, including remove/reinsert and extreme keys.
- Lazy records expose read-through, clone-on-first-write, changed IDs, and boundary snapshot/restore of deltas only. Avoid a whole-map staging iteration API.
- The private deadline index contains waiting requests only. Grant clears/removes the deadline; suspension/restart after a previous grant must not recreate it. Due lookup is <= the causal time. Preserve existing observable timeout record order by PriorityKey, even if the index itself orders by deadline. Reprioritization updates any embedded priority key atomically.
- Replacement returns exactly the existing incoming/victim ordering and exclusions. Stream the already ordered waiting queue; avoid sorting it again. Preserve priority/admission/request tie rules, eligibility and no-match semantics. Analyze and measure eligible as well as ineligible holders.
- Index consistency tests must reject missing or corrupt entries atomically. Cover equal-deadline ties, completion events before and after deadline events at the same tick, grant/cancel/despawn cleanup and reprioritization.

Recommended serial integration order: pure queue overlay and lazy-record overlay (parallel disjoint workers), then one Flow writer integrates causal staging/owned commit, then the same owner implements deadline/replacement reconciliation, then independent full correctness and performance review. Maintenance scans for Remove/Despawn remain explicitly disclosed. Notify/Domain must avoid staging unrelated Flow records. Each implementation leaf requires source-bound packets and independently reviewed interfaces before a Luna writer starts.
