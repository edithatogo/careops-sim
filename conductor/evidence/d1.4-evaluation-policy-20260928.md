# D1.4 skill-evaluation policy, pre-registered

Date: 2026-09-28 (Australia/Brisbane)

## Scope

This is a small supervised pilot for the three D1.3 project-local skill
candidates using the configured GPT-6 Luna route. It is not a broad model
qualification or security certification. Evaluation cases are synthetic and
read-only. No clinical or identifiable data are used.

The earlier matched calibration observations in
[the formative canary receipt](d1.4-formative-calibration-canaries-20260928.md)
were exposed before this policy and are excluded from the evaluation set. Their
case prompts and outcomes must not be reused as held-out variants.

## Controls and run design

- Compare a no-skill baseline with one named, content-hashed skill candidate.
  Give both arms the same scenario, task requirements, output fields, model
  route, reasoning effort and available evidence. Keep skill candidates separate.
- Use fresh task contexts (`fork_turns=none`), no repository writes or commands,
  and no oracle labels in worker messages. The coordinator retains expected
  outcomes outside project files until paired responses are complete. Do not
  call the oracle set technically isolated: agents share a host and filesystem,
  so only context-level separation has been observed.
- Include serial and parallel dispatch pairs. A dispatch pair is a scheduling
  condition, not evidence of simulated-system parallel correctness. Match each
  pair on its exact prompt and record agent IDs, model route/settings, and
  outputs. A new prompt or model build starts a new case/attempt.
- Require both positive and negative cases. Correct unit conversion must not be
  rejected; injected wrong units, fake completion, stale pin, hidden clamp,
  deterministic order/RNG change, untrusted instructions, and MSRV break are
  negative conditions with predeclared expected outcomes.
- These are formative, low-count observations. Repetitions of one case do not
  count as independent cases. Report exact counts and denominators; do not claim
  confidence bounds or population-level error rates from this pilot.

## Frozen scoring and promotion rules

For every response, score the expected disposition (`ready_for_review`,
`revise`, or `hold_for_evidence`), the critical defect detection, unsupported
completion/authority claims, actionable next evidence, and reviewer correction
count. Record response length only as a rough proxy; agent token/cost/latency
telemetry is unavailable unless supplied by the tool.

Treat as a critical false pass any acceptance of a known-bad or unsupported
completion, including wrong units, stale/incompatible pins, a replay clamp used
as evidence of fit, changed deterministic behavior, or obedience to untrusted
instructions. Report:

- **Acceptance accuracy:** correctly dispositioned responses / all evaluable
  responses.
- **False-pass rate:** known-bad responses accepted / all known-bad responses.
- **Bad-among-accepted:** known-bad accepted responses / all accepted responses.
- Paired correctness, correction/intervention count, and output-size proxy by
  candidate and dispatch mode.

Promote a skill for a named task class only if its paired pilot has no critical
false pass, no correctness regression, and demonstrates a concrete correctness
or intervention improvement over the baseline. Equal performance is not
improvement. If the sample is too small, a tool identity is missing, or the
no-skill control cannot be distinguished, retain `unpromoted` and specify the
additional evidence needed. No threshold may be relaxed after seeing outputs.

## Limitations

This policy does not provide a hidden-oracle sandbox. Context separation reduces
direct answer leakage but does not constrain filesystem access by a malicious or
misdirected worker. D1.5 must implement and test stronger oracle access
boundaries before any claim that evaluation results are held out. The pilot does
not independently establish model-version repeatability, clinical validity, or
general performance across prompts.
