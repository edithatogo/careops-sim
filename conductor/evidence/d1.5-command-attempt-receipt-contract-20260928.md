# D1.5 command-attempt receipt contract

Status: coordinator-frozen input contract for the `D1.5.receipts` implementation
leaf. Schema: [version 1 JSON Schema](d1.5-command-attempt-receipt.schema.json).

## Contract decisions

- One receipt describes one immutable packet attempt. `packet_id` identifies
  the reviewed work; `attempt_id` identifies this execution. A retry gets a new
  attempt ID and may name the prior ID in `supersedes_attempt_id`; it never
  overwrites an earlier receipt.
- `base_commit`, the input path/hash map, optional seed hash, command argv/cwd,
  expected and actual exit status, stdout/stderr SHA-256 and byte counts, tool
  versions, output path/hash map, changed paths, UTC timestamps, model metadata,
  status, and unresolved issues are explicit.
- Raw stdout/stderr, private payloads, credentials, and patient data are not
  included. Hashes and byte counts preserve identity/size evidence without
  copying output content into the receipt.
- A worker-submitted receipt is always `worker_reported`; the schema rejects a
  worker claim of `coordinator_captured`. Coordinator-captured execution evidence
  belongs in a separate coordinator-owned record and must be derived from the
  actual execution environment, never copied from a worker field. A syntactically
  valid receipt, hash, test summary, or worker report alone does not prove that a
  command ran or passed.
- Worker status is limited to `ready_for_review` or `blocked`; a worker cannot
  accept a task, promote a skill, mark a phase complete, or claim release.
- The JSON Schema is the format contract. The implementation leaf must validate
  the schema's required fields and no-extra-field rule using only dependencies
  already approved for the parent harness; later D1.5 leaves own dispatch/hash
  rechecks, recovery/checkpoint behavior, writer arbitration, and any enforceable
  oracle boundary.

## Redaction and validation requirements

- Receipt strings are metadata, not payload storage. Include only packet-approved
  argv and normalized repository-relative paths. Do not include environment
  values, credentials, patient/private data, raw output, or arbitrary input
  contents. If an exact argv would expose a secret, stop and use an approved
  secret-safe command interface; do not serialize the secret or silently claim
  an exact argv. `unresolved_issues` must be a short, sanitized operational
  summary, at most 512 characters per item.
- The schema limits paths to normalized relative POSIX paths and rejects drive
  prefixes and backslashes. Apart from `.` for the repository root, reject dot
  segments, repeated separators, and trailing separators. The validator must
  parse UTC timestamps, require attempt start <= finish, require each command
  interval to lie within the attempt interval, and require command start times
  to be monotonic with nonoverlapping intervals (`prior finish <= next start`).
  JSON Schema `format` alone may be annotation-only unless the validator asserts
  it.
- Schema validation cannot prove that free text is free of sensitive data.
  The serializer must apply the redaction policy and tests must cover common
  credential/payload patterns; human review remains required before evidence is
  committed. No regex or hash makes arbitrary private text safe.
- `ready_for_review` requires no unresolved issues, every command's actual exit
  code to equal its expected exit, and every packet-required output to be listed
  with its hash. Otherwise status is `blocked` with a sanitized issue summary.
  The coordinator later recomputes hashes against the bound packet and output
  files. This still does not make worker claims independently verified.

## Verification limits

Schema validation checks structure and digest shape. It does not recompute input
or output hashes, authenticate a worker, verify a Git object, prove command
execution, guarantee free text is non-sensitive, or isolate an evaluation
oracle. Those claims require separately captured evidence in the later D1.5
leaves. No private or clinical data belongs in a receipt.

## Independent contract review

A read-only GPT-6 Luna review identified worker-asserted coordinator capture,
unbounded sensitive free text, timestamp ordering, and noncanonical path gaps.
The contract now restricts worker receipts to `worker_reported`, requires
sanitized packet-approved fields, specifies asserted UTC/order checks, and
rejects Windows and noncanonical paths. The reviewer rechecked the updates and
reported no remaining blocker; the final review also prompted explicit rejection
of dot segments, repeated/trailing separators, and overlapping command intervals.
