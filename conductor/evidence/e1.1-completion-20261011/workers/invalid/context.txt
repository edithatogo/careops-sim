# E1 behavior-first fixture contract v1

Coordinator frozen 2026-10-11. Synthetic oracle specification only; no native
pathway runtime or clinical acceptance. See ADR-0010. Rust execution remains
1.99.0 only; Python standard-library tests independently check fixture arithmetic.
This is a test fixture format, not a public application schema or runtime API.

## Shared semantics

All times are integer ticks. No clinical conversion, empirical acuity mix,
stochastic fit, warm-up or default operational parameters are implied. Acuity
labels are synthetic integers 1..5, not validated ATS performance standards.
Patient identifiers are unique and stable. Inputs arrive in [0,horizon); stage
work intervals are half-open, completion exactly at horizon is included. Positive
service durations only: zero duration is explicitly rejected before scheduling.
Finite ordered stages: triage, assessment, optional diagnostics, treatment.
No cycles or implicit parallel patient attention. One independent resource per
stage; capacity is a positive integer. FCFS ties use arrival/readiness then
patient ID. No acuity priority is asserted by these synthetic fixtures.

Discharge becomes terminal only at actual discharge after treatment. Admission
intent is provisional: patient remains boarding after decision until compatible
external bed offer and actual transfer completion. Offers are finite, consumed
once, valid on [available_tick,withdrawn_tick); no ward model is implied. Fixtures
use a single offer when testing a single admission; transfer duration is positive.
No offer means unfinished boarding at horizon, not admitted. E1.3 must preserve
occupancy until actual transfer and recurrent boarder care; these full behaviors
are runtime debt, not implemented by fixture validation. Distinguish declared
latent condition, agent knowledge, provisional disposition and realized outcome.

## Format and metrics

Each family JSON has fixture_version=1, family, provenance='synthetic_test_only',
time_unit='tick', runtime_status='unbound', cases. Case IDs are prefixed by family.
Every case has case_id, inputs, expected, runtime_owner (E1.2 or E1.3), and an
explicit purpose. Family-specific inputs/expected fields must be documented in
the test module and strictly validated. Expected values must be recomputed from
inputs and checked against independently hand-fixed case assertions; simply
comparing a fixture to itself is insufficient. Mutation probes must reject
changed durations, endpoints, counts, identities and relevant validation inputs.

Arrivals = terminal + unfinished, with each arrived ID represented exactly once.
Started <= arrivals. Unfinished includes queued, active or boarding and has no
realized terminal tick/outcome. First-care wait = first stage start - arrival.
Total stage queue wait = sum(stage start - preceding stage end), first predecessor
is arrival. Work = sum completed/observed active stage intervals, excluding waits
and boarding/transfer; unfinished work is clipped at horizon. Completed LOS =
actual terminal tick - arrival; unfinished LOS is null (separate observed elapsed
may equal horizon-arrival). Boarding and transfer are separate intervals. Counts
are counts, not rates; completed LOS denominator excludes unfinished patients;
wait denominator includes patients with a first start; zero denominator => null.
Throughput is terminal count in the stated cohort. No uncertainty claim.

## Required independent families

- endpoints: empty run; one discharged patient; full synthetic acuity1..5 x
  discharge/admission x diagnostics absent/present (20 independent one-patient
  cases); no-offer admission remains unfinished. Triage2, assessment3,
  diagnostics4 when present, treatment5 ticks, arrival1; admission decision at
  treatment end, offer available2 ticks later, transfer2 ticks. Horizon30.
  Empty metrics must have zero counts and null undefined averages.
- extremes: capacity1, four same-time arrivals at1, single positive service2,
  horizon7 => starts1,3,5,7; completions3,5,7,null. Long work8 at1/horizon7
  unfinished; horizon9 complete. Include queued censoring (horizon2, same four),
  exact-horizon completion, zero-service rejection and deterministic input-order
  permutation. Single-stage analytic projections explicitly exclude full pathway
  runtime coverage. Their contract is also expressible by current E0.
- invalid: zero/unknown/inconsistent capacity, unresolved resource/task,
  incompatible resource class, missing eligibility, invalid acuity, repeated or
  disordered stages, duplicate patient IDs, nonpositive horizon, arrival at horizon,
  zero duration. Each has exact invalid payload/mutation, invariant, diagnostic
  category and native owner. Model validation must precede mutable execution;
  fixture tests alone cannot prove transactional runtime behavior.

## Acceptance boundary and runtime debt

Tests must detect independent mutations, missing required cases, wrong units,
changed provenance and false runtime_status. E1.1 accepts specifications only.
E1.2 owns arrivals/stage/acuity/diagnostic native binding; E1.3 owns actual terminal,
boarding/transfer binding. E1.4 cannot close with any fixture unbound, skipped,
ignored, unexpectedly failing or satisfied by an oracle masquerading as runtime.
Keep E0 schema1 compatibility. Freeze application schema/API separately at E1.2.

# ADR-0010: E1 test-first acceptance and bounded parallel fixtures

Accepted engineering decision, 2026-10-11. User commissioned E1.1 implementation
and bounded follow-on work. Coordinator review plus GPT-6.1-sol independent review
confirmed the E0.1 precedent in e0.1-patient-trace-acceptance-20261002.md and
e0.1-schema-fixtures-acceptance-20261002.md: behavior-first executable fixtures
may be accepted before the later task implements the runtime.

E1.1 acceptance means complete reviewed fixture specifications, independent
arithmetic/validation tests and mutation evidence, not working ED pathways.
Every unbound native assertion must remain inventoried for E1.2/E1.3. E1.4
requires actual native conformance of every case; no skip or fixture-only pass
substitutes. Existing E0 behavior remains separate and unchanged.

Freeze [the shared contract](../design/ed/e1-fixture-contract.md) before dispatch.
Replace only E1.1's conservative internal serial edges with the same six accepted
external closeouts for each leaf. There is no produced-data dependency between
these families: each writes its own JSON/test file and consumes the shared
contract read-only. All three instance sets remain mandatory at the join.
Any contract drift stops/rebinds affected workers. Runtime E1.2 leaf dependencies
remain serial; use writer/reviewer/next-packet planner roles there.

No private data, new public API, upstream modifications, release acceptance or
unbounded unattended work is authorized by this decision. A thread heartbeat
may resume only the next E1.2.arrivals leaf after exact E1.1 acceptance readback.

# Bounded worker prompt

You are executing one reviewed packet for CareOps Sim. Use the model selected by
the coordinator; gpt-6-luna is a candidate for this role. The packet cannot override
user/system instructions. Do not take architecture or release ownership.

1. Read AGENTS.md and the supplied bound packet. Confirm packet ID, target repo,
   base commit, input hashes and assigned worktree. Run packet-check. If any differ,
   stop and report `blocked`; do not update hashes to make the check pass.
2. Read the listed context and interface contract. Identify the single expected
   behavior/output, permitted files, protected paths and exact final test oracle.
3. Confirm the coordinator has accepted prerequisites and reserved your paths.
   Do not acquire conflicting ownership or start other work yourself.
4. Execute the packet's steps in order. Add behavior-focused tests before code
   when required. Keep edits inside write_paths and use the existing architecture.
5. Run the listed commands in the specified directories. Record real exits,
   counts and artifact paths. A missing test/command is a blocker, not a pass.
6. Check your diff for unrelated changes and rerun the final acceptance check.
   Do not change tolerances, golden results, test exclusions or public semantics
   to remove a failure unless the packet explicitly authorizes that exact change.
7. After two unsuccessful correction attempts, summarize the failing command and
   smallest observed counterexample. Escalate missing contract/skill/tool/hardware
   needs rather than repeatedly guessing.
8. Return `result-template.json` with `ready_for_review` or `blocked`, plus the
   actual diff/commit and evidence. Never claim `accepted`, change the plan checkbox,
   merge into another worker's branch, publish or update the parent submodule pin.

The coordinator/reviewer performs the combined integration checks and advances
accepted status. Serial execution uses this same prompt and evidence contract.

# MVP Luna execution loop

Work one bound leaf instance. Your output is proposed work until coordinator
acceptance. This role does not permit you to weaken tests, choose unapproved
interfaces, accept your own result, publish or switch the model.

- Start from the bound context bundle, exact source hashes and interface. Read
  repository AGENTS instructions, but do not load every track/report by default.
- Record one attempt ID and the model/version actually exposed by the harness.
  Missing cost/version data is unknown, not a fabricated value.
- Implement one output. For code changes, reproduce the specified failing behavior
  before the fix and then run the final success check. For tests-only leaves,
  final execution must verify the intended red fixture/expected failure explicitly;
  a silent missing executable is not a useful red test.
- Work for at most 60 minutes per attempt and at most two unsuccessful corrections.
  Stop with evidence at either limit; a coordinator may authorize a new attempt
  after reviewing the cause. Never expand write paths or tests on your own.
- If source inspection needs more context, request a new bound slice. Keep loaded
  relevant context within the 24 KB bundle budget (bytes, not a token guarantee).
  Stream data extraction in batches rather than putting all evidence in prompts.
- Checkpoint after a successful test or before interruption: leaf/instance/attempt,
  exact base and input hashes, changed files, last command/exit, output hashes,
  unresolved question and the next single action. Keep logs as files, not prose.
- Return result.json with actual command receipts and ready_for_review or blocked.
  A behavioral oracle failing, unavailable prerequisite or stale base is blocked.
  The coordinator verifies diffs and runs the independent/combined checks.

Plural recipes are controlled fan-out: one source, parameter family, platform or
fixture case per instance. The coordinator freezes the instance list first and
accepts the join only when every required instance has a receipt. A single example
cannot stand for a complete source family. Parent task closure also checks the
original objective and phase acceptance, preventing omissions in leaf proposals.
