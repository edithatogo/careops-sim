# P0.2 consumer, unit and profile mapping proposal

**Status:** coordinator-authored draft for E0/C0 review; not accepted or frozen.  
**Artifact:** [`parameter-usage-matrix-proposal.json`](../../model-inputs/ed/schema/parameter-usage-matrix-proposal.json)  
**Validator and focused regression:** [`validate_ed_usage_matrix.py`](../../tools/validate_ed_usage_matrix.py) · [`test_ed_usage_matrix.py`](../../tests/test_ed_usage_matrix.py)

## What the matrix adds

The matrix covers all 101 IDs from `parameter-ids.json`, with one proposed
configuration key, the registry's current consumer statement, a unit/value
class proposal, and an MVP/v1/deferred profile-use proposal. Every row says
`proposed_requires_E0_C0_owner_review`; no numeric parameter value, distribution,
clinical rule, or actual profile is asserted.

The proposed ED configuration normalization unit is seconds, converted to
Kairos integer ticks by the E0 model boundary. Timestamped schedules retain an
explicit source timezone and precision. Distance and walking-speed suggestions
are metres and metres/second. Probabilities retain explicit conditioning and
denominators. Composite records put units on numeric leaves. These are review
proposals; C0 must align timestamp origin, precision, conversion and rounding,
and E0 must decide the actual configuration API.

## Verification performed

From the repository root:

```sh
python3 tools/validate_ed_usage_matrix.py \
  --registry model-inputs/ed/schema/parameter-ids.json \
  --matrix model-inputs/ed/schema/parameter-usage-matrix-proposal.json
python3 -m unittest discover -s tests -p 'test_ed_usage_matrix.py' -v
```

Expected output: `PASS: 101 registered IDs have proposed consumer, unit and
profile mappings`. The validator checks one-to-one ID coverage, consumer
consistency, required proposed keys/classes/stages, and the explicit review and
evidence-boundary labels. It does not validate clinical correctness, select
profile values, establish source evidence, or approve a configuration API.
