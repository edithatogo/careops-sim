# P0.3 source verification and extraction protocol

**Scope:** P1 DES and P2 ABM source packets. This protocol qualifies a claim for
review; it does not accept a numeric input, distribution or calibration target.
Each packet starts from one named supplied report/excerpt and one source/family
question. Search the internet only for that packet's recorded primary-source
gap. The report is a lead and lineage record, never its own primary-source
verification.

## Packet input and output

Before dispatch, the coordinator binds report file SHA-256, section and line
span, the parameter IDs from the accepted matrix, source/revision lead or named
gap, exact output path, allowed source family, extraction fields, commands,
oracle and independent reviewer. Use one primary source and narrow parameter
family per packet. If the source cannot be reached, return an `unresolved_gap`
record with owner, impact, searches performed and next action. Do not substitute
an adjacent paper or silently fabricate a value to complete a row.

For a primary claim, capture the retrieved bytes or a stable exported snapshot,
compute their SHA-256, record URL or DOI, revision/edition or immutable repository
commit, exact page/table/field or anchored paragraph or code path/line span,
population/site and period, source units/precision, licence/access terms,
retrieval date, extraction/transformation and verification status. Record report
lineage under a separate `report_lineage` object. A code commit is the canonical
repository revision; publication revision is the edition/date actually read.
When lines are represented as start plus positive count, the last included line
is `line_start + line_count - 1`; reject overflow or a range beyond the source.

The schema checks types, required fields and selected structural exclusions.
It cannot prove that a digest matches the retrieved bytes, that a source passage
supports a claim, that `population`, `period`, `units`, licence or revision strings
are informative, or that transformation units and denominators are correct.
The **independent readback** must therefore retrieve the same pinned source,
recompute the hash, locate the cited field, reproduce the transform and compare
the claim's population, period, unit and denominator. A reviewer records pass,
partial, contradiction or unresolved status with a specific reason. A source
row marked `verified` without this readback remains unaccepted for empirical
profile use.

### Structured independent readback record

Primary-source records use schema version 2 because independent readback is now
a required part of the claim record. The source claim fields and review gate are
otherwise unchanged; synthetic-assumption and unresolved-gap records remain
version 1. A v1 primary record is not upgraded by implication: retain its source
claim and add a v2 readback record before relying on it as accepted evidence.

`independent_readback` records reviewer, date, outcome, reason, and a durable
readback reference. It also records the hash recomputed from the retrieved bytes
and whether it matches `primary_source.source_sha256`, the exact locator checked
and evidence reference, and the transformation method and comparison result.
The schema requires all of these fields. For outcome `pass`, it also requires
the reported hash-match, located-passage, and reproduced-transformation flags
to be true. These booleans and the digest string remain reviewer assertions;
schema validation does not retrieve bytes, recompute hashes, or establish that
the referenced locator or transformation evidence is genuine.

The accepted empirical-source gate is conjunctive: existing `review.outcome`
must be `accepted`, `primary_source.verification` must be `verified`, and
`independent_readback.outcome` must be `pass`, with the recorded hash equal to
the source hash and locator and transformation evidence inspected by the
independent reviewer. `partial`, `contradiction`, or `unresolved` is a visible
non-acceptance that requires a reason and follow-up; it must not be relabelled
as a pass to satisfy the gate. A coordinator still records the row-level
decision after reviewing the cited evidence.
Run `python3 tools/validate_source_acceptance.py RECORD.json` for the
machine-verifiable part of this gate, including digest equality. A passing
command is not proof that the source bytes, cited passage or method are genuine;
the independent source readback receipt remains required.

## Data and modeling boundaries

- Keep source facts, report interpretation, model assumption and observed
  calibration target in separate records. A locally transcribed/derived table
  cites both the report excerpt and original source; it is never described as
  recovery of an unseen standalone bundle.
- A published mean, marginal count or time-to-event aggregate is not a fitted
  distribution, active task duration or patient-level joint distribution.
  Record censoring, missingness, inclusion/exclusion and sample denominator
  before proposing a fit. P3 owns family selection, dependence and uncertainty.
- Capture population transfer limits from non-Australian or site-specific work.
  No Cairns operating value is inferred from generic/public evidence. A
  synthetic example records its assumption rationale and sensitivity need.
- Keep observed occurrence and recorded/message times distinct. Queue, work,
  travel, bed offer, boarding and physical departure intervals cannot be added
  twice merely because each appears in a source table.

Coordinator acceptance requires the worker's command/evidence receipt, exact
source hash and location readback by an independent agent, and a row-level
decision. Failed access, ambiguous denominators, unpublished tables and
conflicting primary evidence remain visible gaps with owner and impact. The
generic model may use an explicitly labelled synthetic assumption while that
evidence gap remains open, subject to P4/P5 profile rules.

## Exact packet mapping guard (P1.2 addition)

Typed source outputs also run [the mapping validator](../../tools/validate_source_packet_record.py):
`python3 tools/validate_source_packet_record.py RECORD --packet-id PACKET_ID`.
It checks the source schema, exact expected parameter-ID set and reserved output
path against the prepared source-family manifest. Validate that manifest with
`tools/validate_p03_packet_plans.py` before binding. A known catalogue ID may still
be the wrong ID for an assigned family; catalogue membership alone is insufficient.
This guard is structural and does not accept sources, values, fits or model use.
