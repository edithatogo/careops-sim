## Finding

The Kairos development branch is seven commits behind and eight commits ahead
of `origin/main` (common base `fae901558f07b7b717a676adbafbe2cdc78dea1c`). The
current DES, ABM, state, type, RNG sources and API compatibility policy match
upstream byte-for-byte. The core scheduler source differs. Upstream fixes a
release-build correctness defect by removing a pending-event entry outside
`debug_assert!`; otherwise release builds omit that removal. It adds tests for
that behavior and scheduler boundaries.

The proposal's main architectural observations remain current: DES and ABM
still have separate contexts; no FlowRuntime/queue/preemption API exists; the
protected-surface inventory still has no exact `crates/kairo-ecs-des` root;
and the API-review template still requires exact-root registration. The upstream
change therefore does not resolve the Track 01/03/25 owner gates.

## Disposition and follow-up

1. Keep ADR-0003's reviewed source pin explicit; do not rewrite its baseline hash
   or claim it describes the current upstream core source.
2. Before Q1 implementation, bring the Kairos development branch onto an
   owner-reviewed current upstream base and rerun the relevant source/API review.
   Do not merge the broad upstream delta or copy core source changes without
   Kairos Track 01 ownership review.
3. Track 01/03/25 owner dispositions remain required. The user is the Kairos
   owner, but prior general approval does not record the specific technical
   dispositions listed in the gate proposal.
4. This refresh accepts no Q0.1 leaf or phase and authorizes no queue code.
