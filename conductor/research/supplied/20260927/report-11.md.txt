# Single-person context and agent harness evaluation for CareOps Sim

## Decision memo

**Research date:** 27 September 2026, Australia/Brisbane.

**Decision:** retain Kairos/KairoECS simulation semantics unchanged and evaluate a **separate development-assistant harness** built around immutable worker packets, isolated Git worktrees, an explicit dependency DAG, disjoint-path parallelism, one authoritative integration writer, deterministic preflight/acceptance gates, content-addressed provenance, stale-context rejection, and fresh review. This is an evaluation recommendation, not an assertion that these capabilities are already implemented.

The inspected public Kairos revision is **`fae901558f07b7b717a676adbafbe2cdc78dea1c`**, dated 19 May 2026, with Git parent **`f11e0be7dcf8cad705741a44b651ca953e269ae2`**. The latter is simply the Git parent of the inspected commit; it must **not** be treated as the project's separately referenced “parent pinned snapshot”, because the attachment defining that snapshot was unavailable here. fileciteturn2file0L3-L7 fileciteturn3file0L1-L2

The recommendation is deliberately conservative because the public repository already expresses much of the required governance model. `conductor/workflow.md` defines owned paths, blocked paths, dependencies, parallel-safe tracks, acceptance and quality gates; it also says cross-track fixes should be handed off rather than casually changed by the current track. fileciteturn11file0L2-L6 `conductor/tracks.yaml` represents status, dependencies, owned paths and required gates explicitly. fileciteturn12file0L2-L6 `implementation-readiness.md` distinguishes planning from actual review/completion and requires concrete evidence such as owned files, commands and waivers. fileciteturn10file0L2-L6 The public workspace also specifies Rust 1.76 and Apache-2.0 licensing and forbids unsafe code at workspace level. fileciteturn8file0L2-L6

Accordingly, the harness should **mechanise existing contract-first development rules rather than invent a second source of truth**. The simulation runtime and development harness should use unambiguous vocabulary:

| Term | Meaning | Status |
|---|---|---|
| `sim_agent` | An entity/behaviour participating in a CareOps/KairoECS DES/ABM model and therefore subject to the model's clock, event ordering, state and seed contracts. | **policy definition** |
| `dev_worker` | An external coding/review assistant operating on source artefacts outside simulated time. | **policy definition** |
| `integration_controller` | The sole process/person authorised to advance the authoritative integration branch and integration ledger. | **proposed policy** |
| `worker_packet` | Immutable, content-addressed task contract for one development attempt. | **proposed policy** |
| `run_record` | Immutable evidence/provenance record for one attempt. | **proposed policy** |

This separation avoids a category error: model-development assistants must never acquire simulation authority merely because both are colloquially called “agents”.

The inspected public README/searchable sources describe KairoECS around deterministic event scheduling and DES/ABM functionality, while conformance material refers to deterministic ordering. fileciteturn7file2L26-L35 fileciteturn7file14L180-L189 Nothing found in this review justifies changing those runtime contracts for the sake of development-agent orchestration.

**Recommended option:** evaluate **OPT-002, dependency-aware isolated workers**, against a serial baseline before adopting it. Do not adopt a fully autonomous reviewer/repair swarm at this stage. No empirical accuracy, cost or latency result exists yet; all promotion thresholds below are explicitly proposed policy rather than observations.

## Evidence base and bounded assessment

### Search and inclusion strategy

The review prioritised original sources: the public Kairos repository at an immutable commit, official Git documentation, official GitHub repository-protection documentation, the current SLSA specification, official OpenAI model/skills/evaluation documentation, original Agent Skills repositories/specification, and the original SWE-bench publication. Secondary commentary was not used to establish architectural or version facts.

Sources were included where they directly informed at least one of: task isolation, dependency scheduling, ownership, staleness detection, provenance, review/recovery, version-pinned skills, model availability or evaluation methodology. Sources were excluded when they concerned detailed surgery, birthing, outpatient, waitlist, whole-hospital or whole-health modelling; when they merely repeated primary documentation; or when they implied implementation capabilities not visible at the inspected Kairos revision.

The public repository was inspected at `fae901558f07b7b717a676adbafbe2cdc78dea1c`; the review did **not** substitute `main` for that revision when making repository-specific conclusions. Its roadmap remains planning evidence rather than proof of implemented capability. fileciteturn9file0L1-L10

### Important evidence limitation

The attachment set named in the research prompt—particularly `conductor/module-readiness.md`, `agent-engineering.md`, `execution-model.md`, the development-readiness materials, generic-ED specifications/plans and the recorded “parent pinned snapshot”—was **not available as an attachment in this session and was not found as an assessable equivalent in the inspected public repository**. Consequently:

* no claim is made that the recommendations conform to the unavailable `agent-engineering.md` or `execution-model.md`;
* no comparison can be made between `fae901...` and the user's separately pinned snapshot;
* no claim is made that a harness, worker packet schema, one-writer controller, stale-context detector or evaluation runner already exists;
* no ED service-time or other clinical parameter has been inferred; all unit fixtures below are deliberately synthetic software-evaluation data.

This is particularly important because the existing readiness documentation itself warns against converting plans into “done” status without checked-in implementation and evidence. fileciteturn10file0L2-L6

### Primary external evidence

Git's worktree mechanism permits multiple working trees attached to one repository, making it a suitable primitive for keeping individual development attempts physically separate while sharing the object database. Git also supplies `merge-base --is-ancestor`, which is useful as one—but not sufficient—staleness check. citeturn11view4turn11view5 A packet can therefore be refused when its base is no longer an ancestor of the integration head, but an ancestor check alone cannot establish that its declared dependency files or semantic inputs remain unchanged; those need explicit digests.

GitHub's CODEOWNERS and protected-branch mechanisms show established ways of requiring designated review and invalidating approvals as new commits arrive. They support the general review/ownership pattern, but CODEOWNERS is **not** an exclusive-writer lock and should not be misrepresented as one. citeturn11view6turn11view7

SLSA **v1.2** is the current specification observed in this review and supplies a useful vocabulary for recording build/source provenance. The proposed CareOps records are only **SLSA-inspired**; no SLSA compliance claim is warranted by this research. citeturn11view8

OpenAI's official GPT-6 Luna documentation confirms that **GPT-6 Luna is actually available as a documented model**, rather than merely a hypothetical name. The documentation describes it as a focused/high-volume model with a 1,050,000-token context window, up to 128,000 output tokens, a 18 May 2026 knowledge cut-off, and selectable reasoning effort. citeturn11view1 That makes it reasonable to include Luna as an experimental “simpler/cheaper worker” arm, but its documentation is not evidence that it will satisfy Kairos-specific safety gates.

OpenAI's current Skills documentation describes skills as reusable, versioned instruction/support bundles and describes compatibility with the Agent Skills format. It also warns that skill content must be treated as potentially untrusted. citeturn11view2 OpenAI's systematic skill-evaluation guidance specifically recommends controlled evaluations and deterministic checks for failure modes such as failure to trigger a skill, skipping required steps and creating unexpected extra files. citeturn11view0 Those methods transfer directly to the requested out-of-scope-edit and fake-pass fixtures, although the CareOps promotion criteria remain project policy rather than OpenAI recommendations.

SWE-bench is useful evidence that repository-agent performance can be evaluated against executable issue-resolution oracles: the original benchmark contains **2,294 real GitHub issues from 12 popular Python repositories**. citeturn11view9 CareOps should borrow the executable-oracle idea, not the benchmark contents: tiny private Rust fixtures are preferable here because they make ownership, dependency, provenance and unit errors directly testable and reduce benchmark-contamination concerns.

## Recommended harness contract

### Worker packet and durable context

Each attempt should begin from an **immutable packet**, ideally canonical JSON or YAML whose bytes are SHA-256-digested before launch. The minimum schema is:

```yaml
# PROPOSED SCHEMA — not an implemented Kairos capability
packet_schema: "careops-worker-packet/v0"
packet_id: "PKT-..."
packet_digest: "sha256:<computed-before-launch>"

repository:
  url: "https://github.com/edithatogo/kairos"
  base_sha: "<40-hex immutable commit>"
  expected_integration_head: "<40-hex or explicit policy>"

task:
  statement: "<bounded task>"
  owned_paths: ["<glob-or-path>"]
  blocked_paths: ["<glob-or-path>"]

dependencies:
  - dependency_id: "<stable-id>"
    accepted_commit: "<commit-or-null>"
    artefact_sha256: "<sha256-or-null>"
    semantic_role: "<why required>"
    units: "<units-or-N/A>"

required_inputs:
  - path: "<path>"
    sha256: "<digest>"
    role: "<input role>"
    units: "<units-or-N/A>"

skills:
  - source_repository: "<exact repo URL>"
    commit: "<immutable commit>"
    path: "<SKILL.md path>"
    blob_or_content_sha256: "<digest>"

execution:
  model: "<exact provider model ID>"
  model_snapshot: "<snapshot if provider exposes one; otherwise unknown>"
  reasoning_effort: "<declared>"
  network: "deny|allow-listed"
  package_install: "deny|allow-listed"
  allowed_commands: ["<exact or patterned commands>"]
  budget:
    max_tokens: "<policy or unknown>"
    max_cost: "<policy or unknown>"
    max_wall_seconds: "<policy or unknown>"

acceptance:
  visible_gates: ["<gate IDs>"]
  hidden_oracle_id: "<not worker-readable>"
  required_outputs: ["<artefact IDs>"]

lineage:
  parent_packet_id: null
  repair_of_run_id: null
```

The principle is **durable context by explicit artefact, not by remembered conversation**. A worker should need only its packet, the exact checked-out repository state, declared dependency hand-offs and authorised skills. Narratives may supplement those records, but should never override hashes, commits, ownership or units. This extends the repository's existing explicit dependencies/owned-path concept rather than replacing it. fileciteturn11file0L2-L6 fileciteturn12file0L2-L6

### Scheduling and one-writer ownership

Construct a DAG from declared packet dependencies. A packet is runnable only when every predecessor has an accepted immutable result. Two runnable packets may execute concurrently only when their owned-path sets are disjoint **and** they do not mutate another shared artefact such as a generated registry, lockfile or common manifest. This is stricter than checking file names after the fact and is intentionally aligned with the repository's notion of “parallel-safe tracks”. fileciteturn11file0L2-L6

Workers should write only in detached/isolated worktrees. The **integration controller alone advances the integration branch**. Workers return candidate commits/diffs plus run records; they do not push directly into authoritative integration state. Git worktrees provide an appropriate isolation primitive for this arrangement. citeturn11view4

This does not preclude parallel computation: workers A and C can run simultaneously when independent, while B waits on A. What stays serial is the authoritative acceptance/integration transaction.

### Staleness and provenance

Run stale checks twice: immediately before worker invocation and again immediately before acceptance.

At minimum verify:

1. declared `base_sha` remains admissible against the current integration head;
2. every accepted dependency commit/digest still exactly matches;
3. all required-input digests still match;
4. every skill commit and skill-file digest still matches;
5. the candidate worktree started from the recorded commit and was clean;
6. candidate changed-paths are a subset of owned paths.

`git merge-base --is-ancestor` is suitable for item 1, but it must not stand in for items 2–4. citeturn11view5 A stale packet should be **invalidated and reissued**, not silently rebased, because silent rebasing changes the evidence context under which the worker made its decisions.

A run record should capture:

```json
{
  "run_id": "RUN-...",
  "packet_id": "PKT-...",
  "packet_sha256": "sha256:...",
  "provider": "...",
  "model_id": "...",
  "model_snapshot": "unknown-or-exact",
  "reasoning_effort": "...",
  "harness_commit": "...",
  "skills": [{"repository":"...","commit":"...","path":"...","sha256":"..."}],
  "base_sha": "...",
  "candidate_head_sha": "...",
  "commands_log_sha256": "...",
  "exit_codes": [],
  "stdout_stderr_sha256": "...",
  "test_result_sha256": "...",
  "changed_paths": [],
  "input_tokens": null,
  "output_tokens": null,
  "provider_reported_cost": null,
  "started_at": "...",
  "finished_at": "...",
  "wall_latency_ms": null,
  "decision": "accept|reject|escalate",
  "decision_reason_codes": [],
  "human_interventions": 0,
  "repair_of_run_id": null
}
```

These fields are proposed provenance, not observed data. SLSA v1.2 is useful background for making provenance verifiable and tied to immutable inputs, but the record above is project-specific. citeturn11view8

### Review and recovery

Acceptance should be ordered so inexpensive deterministic checks fail first:

**scope/preflight → build/test/static gates → hidden functional oracle → independent review → integration**.

A worker saying “tests pass” has zero evidentiary value unless the harness itself obtains the required command result from the isolated worktree. Similarly, a reviewer model cannot waive a failed deterministic gate. OpenAI's skills-evaluation guidance explicitly uses deterministic graders to catch concrete output/process failures, which supports this pattern. citeturn11view0

A rejected attempt remains immutable. Repair creates a **new packet ID and new run ID**, pointing to the failed run and containing only the failure evidence authorised for disclosure. A cross-owned-path problem is handed to the owning packet/track; it is not permission for the current worker to broaden scope. That matches the existing Kairos workflow's hand-off model. fileciteturn11file0L2-L6

A retry limit of one or two attempts may be worth evaluating, but that number is **policy/synthetic**, not evidence-backed. Repeated failure should escalate rather than allowing autonomous scope expansion.

## Held-out evaluation programme

### Experimental design

Start with **20 unique tiny private fixtures × three repetitions per configuration = 60 runs/configuration**. This sample size is **proposed/synthetic** and intended as a pilot, not a statistical certification.

Each fixture should be instantiated before the model sees it, with the decisive checks placed in a worker-inaccessible oracle. Where possible, create structurally equivalent but non-identical variants for later promotion testing. Randomise configuration order to reduce temporal/provider-load confounding, and pin all available model, prompt, skill, harness and repository identifiers.

Use at least these arms:

| Arm | Worker | Skills | Purpose |
|---|---|---|---|
| A | stronger reference model selected at execution time | none | baseline |
| B | **GPT-6 Luna**, exact available model ID/snapshot recorded | none | simpler-model test |
| C | same model as B | one relevant immutable skill | estimate skill effect |
| D | reference worker | same relevant immutable skill | test interaction |
| E | no worker invocation | deterministic harness only | verify that preflight cases are correctly blocked without spending tokens |

GPT-6 Luna's inclusion is justified because it is a currently documented OpenAI model; its performance in this harness is entirely unknown until measured. citeturn11view1

Do **not** let the evaluation skill leak hidden acceptance rules. OpenAI's controlled skill-evaluation approach makes a no-skill control especially important. citeturn11view0turn11view2

### Metrics

For each run define oracle outcome `accept`, `reject` or `escalate`, and compare it with the harness decision.

**Acceptance accuracy**  
\[
\frac{\text{correct accept/reject/escalate decisions}}{\text{all evaluable runs}}
\]

**False-pass rate — primary safety definition**  
\[
\frac{\text{known-bad runs accepted}}{\text{all known-bad runs}}
\]

Also report **bad-among-accepted**, because teams often use “false pass” ambiguously:

\[
\frac{\text{known-bad runs accepted}}{\text{all accepted runs}}
\]

**Intervention rate**  
\[
\frac{\text{runs requiring human intervention}}{\text{all runs}}
\]

Also report interventions per ultimately accepted task, because repeated repairs can hide labour in a superficially high task-success rate.

**Cost:** use provider-reported actual charge where exposed, together with input/output/cached token counts. Do not manufacture dollar cost from a price table when billing metadata is unavailable; record it as `unknown`.

**Latency:** record wall-clock run latency, model-call latency if available, and complete DAG critical-path makespan. Report median and 95th percentile rather than only the mean.

For binomial outcomes, report confidence intervals. With only **30 negative runs**, observing zero false passes does not demonstrate a tiny underlying error rate: the traditional “rule of three” gives an approximate 95% upper bound of about **10%**. A promotion set with 60 independent negative observations and zero failures only reduces that rough upper bound to about **5%**. These are statistical consequences of the proposed sample sizes, not observed results.

A sensible promotion rule is therefore comparative rather than pretending the pilot establishes absolute safety: **zero observed critical false passes on scope, dependency, provenance and unit traps; no material accuracy/intervention regression versus the reference configuration; and demonstrated cost or latency benefit**. Any numerical allowed degradation, such as five percentage points, should be recorded as **project policy** rather than disguised as literature-derived fact.

### Required fixture behaviours

The fixture set deliberately includes the user's requested failure classes:

* fake pass;
* correct result accompanied by out-of-scope edits;
* missing dependency;
* wrong units;
* stale base and stale dependency digest;
* false parallel safety;
* reviewer-only invariant failure;
* provenance mismatch;
* skill drift;
* dirty/wrong worktree;
* attempted repair outside ownership.

No fixture uses or estimates ED service times. `1.5 s = 1500 ms` in the unit fixture is **synthetic software test data**, not a healthcare model parameter.

### `commands.sh`

```bash
#!/usr/bin/env bash
# PROPOSED / UNEXECUTED COMMAND FIXTURES.
# These are harness-design examples, not a claim that they are supported by current Kairos automation.
set -euo pipefail

# CMD-001 — Record immutable starting identifiers.
git rev-parse --verify HEAD
git status --porcelain=v1

# CMD-002 — Create an isolated detached worker tree.
git worktree add --detach ".harness/worktrees/${RUN_ID}" "${BASE_SHA}"

# CMD-003 — Test the packet base against the authoritative integration head.
# Interpretation of failure is harness policy; this check alone is NOT sufficient staleness detection.
git merge-base --is-ancestor "${BASE_SHA}" "${INTEGRATION_HEAD}"

# CMD-004 — Verify exact required artefact digests.
sha256sum --check "${PACKET_DIGEST_CHECK_FILE}"

# CMD-005 — Enumerate candidate changed paths for ownership validation.
git diff --name-only "${BASE_SHA}...HEAD"

# CMD-006 — Machine-check that no uncommitted artefact has escaped the candidate record.
git status --porcelain=v1

# CMD-007 — Rust formatting gate when listed in the packet.
cargo fmt --all -- --check

# CMD-008 — Targeted Rust test gate; crate/filter MUST come from the packet, not this template.
cargo test -p "${CRATE}" "${TEST_FILTER}"

# CMD-009 — Optional lint gate only when required by the packet/project toolchain.
cargo clippy -p "${CRATE}" --all-targets -- -D warnings

# CMD-010 — Record the candidate commit only after worker completion.
git rev-parse --verify HEAD

# CMD-011 — Re-run dependency/input/skill digest validation immediately before acceptance.
sha256sum --check "${PRE_ACCEPT_DIGEST_CHECK_FILE}"

# CMD-012 — Remove the isolated worktree only after logs, hashes and candidate commit are durably recorded.
git worktree remove ".harness/worktrees/${RUN_ID}"
```

**Record count: 12 proposed command groups. None was executed in this research.** `git worktree` and `git merge-base --is-ancestor` are based on the official Git interfaces. citeturn11view4turn11view5 The Cargo commands are candidate gates only; whether a particular crate/filter/clippy invocation is valid must come from the packet and repository at the pinned revision.

# Decision memo — CareOps development-assistant harness

Research date: 2026-09-27 Australia/Brisbane
Status: proposed evaluation decision, not implementation approval

## Decision

Evaluate OPT-002 against OPT-001.

OPT-002 consists of:
- immutable content-addressed worker packets;
- isolated Git worktrees;
- explicit dependency DAG;
- parallel execution only for ready workers with disjoint ownership and no shared mutable artefact;
- exactly one authoritative integration writer;
- base, dependency, required-input and skill freshness checks before invocation and acceptance;
- deterministic scope/build/test/hidden-oracle gates before model review;
- immutable run provenance;
- rejection followed by a new repair packet rather than mutation of historical evidence.

Do not modify KairoECS simulation clock, state, event ordering or seed contracts for this harness.
Use `sim_agent` only for simulation participants and `dev_worker` for development assistants.

## Experimental decision

GPT-6 Luna is an eligible test arm because current official documentation confirms availability.
Its suitability for Kairos is unknown and must be measured.

Run a private synthetic pilot:
20 fixtures x 3 repetitions x each configuration.

Primary safety metric:
false_pass_rate = bad_runs_accepted / all_bad_runs

Also measure:
decision accuracy,
bad-among-accepted,
task success,
human interventions,
provider-reported cost,
token counts,
wall latency,
model latency where available,
DAG critical-path makespan.

Do not estimate unavailable billing values.

## Promotion principle

No automatic promotion from "latest" versions.
No automatic promotion from lower cost or lower latency.

A simpler worker becomes a candidate for routine bounded packets only if:
1. no critical false pass is observed for ownership, dependency, provenance and unit traps on the agreed promotion set;
2. decision/task accuracy and intervention burden are not materially worse than the reference configuration under predeclared project-policy margins;
3. lower cost and/or latency is actually observed;
4. all artefact/model/skill versions are pinned and reproducible.

The exact allowable degradation margin is a project policy decision, not a published empirical constant.

Any adoption of OPT-002 should be reviewed as a development-process change.

## Conflicts, unresolved questions and prioritised evidence acquisition

The main architectural conflict is not between the proposed harness and Kairos: the inspected Kairos workflow already favours explicit dependencies, owned paths, quality gates and cross-track hand-off. fileciteturn11file0L2-L6 The real risk is introducing a development-agent system that becomes a **second implicit state machine**—with chat memory, floating skills or autonomous integration decisions—beside those existing contracts. The proposed packet/DAG/one-writer design is intended to prevent that.

There is also a genuine tension between throughput and context integrity. Parallel workers can reduce makespan, but only when independence is established in advance. File-level disjointness is insufficient where both jobs alter a logically shared generated artefact or depend on a moving semantic interface. The safe default is therefore “blocked unless dependency and ownership conditions prove readiness”, not “parallel unless a collision happens”.

Version freshness creates another conflict. The stable Codex release observed during research is a candidate, while newer prereleases exist; neither “stable” nor “newer” establishes Kairos compatibility. Likewise, a skill being compatible with the Agent Skills format does not establish that putting it into context improves this task. OpenAI's own documentation supports versioned skills and controlled evaluation rather than assuming benefit. citeturn11view2turn11view0

The highest-priority evidence-acquisition actions are:

1. **Recover and hash the missing project evidence first:** the exact pinned snapshot plus `module-readiness.md`, `agent-engineering.md`, `execution-model.md`, development-readiness and generic-ED materials. Compare those files against `fae901...`; do not merge this report's proposals into project doctrine before that comparison.
2. **Implement only a minimal evaluator prototype**, beginning with OPT-001 plus packet validation, worktree isolation, changed-path checks and run-record capture. Then add the DAG scheduler needed for OPT-002. This preserves a valid serial control condition.
3. **Generate the 20 private fixtures and hidden oracles before model testing**, freeze their hashes, then execute the same fixture/repetition matrix against the reference model and GPT-6 Luna. Until that happens, acceptance accuracy, false-pass rate, interventions, cost and latency are all **unknown**, not zero.
4. **Recheck upstream immediately before execution:** exact OpenAI model identifiers/snapshots, current stable Codex release and relevant open issues; then compatibility-test against the pinned Kairos Rust/toolchain rather than approving versions from publication dates alone.
5. **Evaluate skills as treatments, not dependencies.** Pin the Agent Skills specification and each skill by immutable commit plus content digest; begin with no-skill controls, and use `skill-creator` only where the fixture actually concerns skill authoring. Never install an upstream skill merely to “try it”.
6. **Set promotion thresholds before seeing results.** In particular, define which false passes are “critical”, the acceptable confidence bound, the maximum intervention burden and the cost/latency trade-off. Otherwise the selection criterion can drift after observing model performance.

The strongest conclusion supported by the available evidence is therefore narrow: **CareOps can evaluate development assistants without changing Kairos simulation architecture by turning its existing ownership/dependency discipline into explicit, content-addressed worker contracts and deterministic acceptance evidence. Whether GPT-6 Luna, any skill, or parallel workers actually improve the cost–latency–reliability frontier remains an empirical question, and no result in this report should be read as having answered it.**
