# Rust-native Metal and MLX assessment for CareOps Sim

**Research date:** 27 September 2026, Australia/Brisbane.  
**Decision status:** **no production backend change recommended yet**. The evidence supports a bounded benchmark phase: retain the existing Kairos CPU-authoritative architecture, evaluate current wgpu/WGSL-on-Metal as the primary device path, and use MLX as an Apple-Silicon comparator for genuinely batch-numeric work. Event ordering, the authoritative clock/state, resource decisions and the Kairos seed/RNG contract should remain on their approved CPU path.

## ED workload fit and data-movement economics

The central technical distinction is not “CPU versus GPU”; it is **regular batched numerical work versus irregular stateful scheduling work**.

The following workload set is therefore **synthetic/proposed**, with stable IDs. No row claims to describe an observed Cairns or generic-ED batch size.

| Stable ID | Inputs | Model output / validation target | Device suitability | Synthetic scenario range | Observed range |
|---|---|---|---|---|---|
| **K-ELT** | Dense SoA f32 arrays of predictions/reference values | Residuals, clamps, branch-light transforms | High | N = 4,096; 65,536; 1,048,576; 16,777,216 | **Unknown** |
| **K-W1-PRESORT** | Two equal-length **already sorted** vectors | Scalar one-dimensional W1 | High for reduction; sorting explicitly excluded | Same N range | **Unknown** |
| **K-KS-CDF** | Two already-built empirical CDF vectors | Scalar KS maximum distance | High for reduction | Same N range | **Unknown** |
| **K-HIST** | Dense observations + fixed bin definition | Exact integer counts | Moderate/high; atomic contention is a useful stress case | N = 65,536 to 16,777,216; 64/256/1,024 bins | **Unknown** |
| **K-SCAN** | Histogram/count vector | Prefix counts/CDF | Moderate; worthwhile only above dispatch overhead | 64 to 1,048,576 elements | **Unknown** |
| **K-CAND** | Predictions/objective inputs for independent parameter candidates | Per-candidate calibration scores and ranking | High when simulation outputs already exist | 8/32/128 candidates × 4,096/65,536 observations | **Unknown** |
| **K-SORT-FULL** | Unordered raw samples | Full W1/KS preparation + metric | Conditional | N = 4,096; 65,536; 1,048,576 | **Unknown** |

The crucial separation is **K-W1-PRESORT versus K-SORT-FULL**. A fast GPU reduction over sorted vectors is not evidence that the full W1/KS pipeline is fast if sorting or empirical-CDF construction dominates. The benchmark contract therefore forbids reporting the reduction-only time as the full calibration metric time.

The natural acceleration target for bounded grid search is likewise the **independent candidate scoring stage** after simulation outputs have been produced. It is not evidence for accelerating the DES itself. An irregular future-event queue, tie-breaking, capacity/resource transitions, Suspend/Abort/Restart state changes and subsequent deterministic scheduling should stay on the CPU path. This follows both the existing Kairos GPU architecture, which leaves orchestration and validation on CPU, and the basic economics of device dispatch. fileciteturn14file0L2-L2 MLX’s own unified-memory documentation gives an illustrative example where very small repeated operations are better on CPU because they are GPU-overhead-bound, despite sharing the same memory pool. citeturn17search0

### wgpu transfer path

Apple Silicon changes the meaning of “host/device transfer” but does **not** make transfer accounting disappear. Metal shared storage lets the CPU and GPU access system memory, and shared mode is the default for buffers and textures on Apple-silicon GPUs; Apple still requires scheduled accesses on one processor to complete before the other accesses the same shared resource. citeturn16search0turn16search4

At the wgpu API layer, `Queue::write_buffer` immediately copies the caller’s bytes into staging memory. `StagingBelt` exists specifically to make many small staging allocations cheaper. citeturn16search7turn16search30 On readback, mapped-buffer access and GPU use are mutually exclusive; mapping therefore introduces an explicit synchronisation boundary even on unified-memory hardware. citeturn16search5turn16search10

The practical inference is that **PCIe bandwidth is the wrong cost model for an Apple-silicon benchmark**, but “zero cost” is equally wrong. The relevant measured quantities are host-side copying/staging, command encoding/submission, cache/coherency and synchronisation, mapping/readback, and whether buffers remain resident across a chain of kernels. citeturn16search0turn16search7turn16search10

### MLX transfer path

MLX is deliberately designed around Apple Silicon unified memory: MLX arrays live in the common memory pool and an operation can be scheduled on CPU or GPU without a conventional explicit device-transfer operation. citeturn17search0turn17search2 That makes it an important comparator.

However, this does **not** establish zero-copy ingress from existing Kairos `Vec`/Arrow-derived CPU buffers. MLX’s official interoperability documentation explicitly states that creating an MLX array from a CPU tensor copies data into MLX-owned storage. DLPack can provide zero-copy import for Metal tensors in suitable circumstances when the underlying Metal buffer is not private, but an equivalent safe Rust/Kairos path has **not been established in this research**. citeturn17search1

The MLX benchmark must therefore time four distinct states: host-owned Rust input → MLX array creation; resident MLX GPU computation; evaluation/synchronisation; and export to a host-owned result. A second resident-data experiment should upload/create once and execute 10 and 100 operations before export. Only the latter tests MLX’s strongest architectural case.

MLX is also lazy, and the first call through `compile()` builds a graph, optimises it, generates code and compiles it. Cold compile time therefore cannot be mixed into hot steady-state timing or silently excluded from one-shot timing. citeturn17search3

## Determinism and numerical contract

WGSL does not support a portable “same floating bits on every backend” contract. The current specification defines f32 and optionally f16 shader floating types and deliberately gives GPU-portability latitude in floating evaluation; WGSL does not specify a single rounding mode for all operations and permits implementation-dependent behaviour within stated accuracy bounds. citeturn16search3turn16search16 This is enough to rule out bitwise cross-device f32 equality as a sensible general CareOps contract.

MLX requires the same distinction. Its GPU path does not support `float64`; f64 arrays are CPU-only. citeturn17search5 Moreover, MLX may use reduced internal precision for float32 matrix-multiplication-family operations unless `MLX_ENABLE_TF32=0` is set, so that environment setting must be logged whenever matmul/convolution/attention-like fixtures are introduced. citeturn17search4

MLX random functions use an implicit global PRNG by default and are based on a splittable Threefry counter PRNG, with explicit keys available. citeturn17search6 That is useful MLX behaviour but **not evidence of equivalence to Kairos’s seed contract**. The initial device fixtures should therefore contain deterministic arrays generated by the existing Kairos host RNG path; MLX or WGSL must not silently generate replacement stochastic inputs.

I propose the following reviewed contract, with status **policy**, not implemented capability:

| Contract class | Required behaviour |
|---|---|
| **D0 — authoritative exact state** | Event timestamps in their approved representation, sequence/tie-break keys, entity/resource identifiers, queue/resource decisions, run/seed identity and RNG stream/state remain exact and CPU-authoritative. |
| **D1 — exact integer numeric outputs** | Histogram counts, scans of integer counts and similar kernels must agree exactly when overflow is excluded. |
| **D2 — floating elementwise outputs** | Compare with a declared CPU reference using max absolute error, max relative error and, for f32 diagnostics, ULP error. Cross-device bit identity is diagnostic only. |
| **D3 — reductions and calibration objectives** | Compare W1/KS/objective differences against a CPU f64 reference where applicable; enforce mathematical invariants and record error as a function of N. |
| **D4 — decision stability** | Calibration acceleration must record ranking correlation, winning-candidate identity and threshold flips. A numerically “small” objective difference is not sufficient if it changes the selected parameter set. |
| **D5 — repeated execution** | Repeat identical fixtures on a fixed backend/device; exact outputs must hash identically where exactness is required, while floating repeatability is recorded rather than assumed. |

A production numeric tolerance is deliberately **unknown**, rather than fabricated. The first correctness pass should generate frozen error distributions before performance is used in an adoption decision. A reviewed tolerance can then be registered per kernel/dtype/size class. That avoids either an unjustifiably loose universal epsilon or a false promise of bitwise equivalence that WGSL and MLX do not provide. citeturn16search16turn17search4

If a device result eventually influences a future event time, the deterministic pattern should be: compute values into a fixed-index result vector; synchronise; validate/reconcile them on CPU in stable index order; and only then perform authoritative event insertion/tie-breaking on the existing scheduler path. That preserves the one-state/one-clock architecture while still allowing batch arithmetic to be accelerated.

## Benchmark and evaluation design

The existing Track 32 single-thread baseline remains useful for continuity, but an ED device decision should be based on **end-to-end break-even against the actual multicore CPU implementation used in CareOps**, on the same host. A GPU kernel that is 20× faster after its operands are resident can still lose when a one-shot ED scoring array is created, submitted, synchronised and read back. Conversely, an accelerator can be valuable when calibration can keep the same arrays resident across many candidate operations. This is precisely why the benchmark separates timing layers. The existing Track 32 single-thread target is documented in Kairos, but this multicore comparison is an explicit proposed addition for this evaluation. fileciteturn12file0L2-L2

The **synthetic** fixture protocol delivered with this report specifies 10 warm-up iterations, 50 measured iterations and 100 identical-input repeatability runs. Those counts are policy/test-design choices, not published performance facts. Each backend records raw samples as well as median/p95/min/max.

For each kernel/backend/size, record:

1. cold runtime/device/pipeline or graph initialisation;
2. hot kernel time with resident inputs, where trustworthy device timestamping exists;
3. host ingress;
4. synchronisation/readback;
5. complete one-shot wall time;
6. upload once → 10 kernels → download once;
7. upload once → 100 kernels → download once;
8. peak memory and all correctness metrics.

The CPU side should include both a single-thread reference and the production-intended multicore path. The host record should contain exact Apple SoC/model, CPU/GPU core counts, RAM, macOS build, Xcode/SDK, Rust compiler, backend/runtime versions and power conditions. **None of those hardware values is populated here because no target machine was specified or benchmarked.**

The most useful decision output is not a single speedup number but a **break-even curve**:

\[
S_{\mathrm{e2e}}(N)=
\frac{T_{\mathrm{CPU,multicore}}(N)}
{T_{\mathrm{ingress}}(N)+T_{\mathrm{device}}(N)+T_{\mathrm{sync/readback}}(N)}
\]

and, for resident chains,

\[
S_{\mathrm{resident}}(N,k)=
\frac{\sum_{i=1}^{k}T_{\mathrm{CPU,multicore},i}}
{T_{\mathrm{ingress}}+\sum_{i=1}^{k}T_{\mathrm{device},i}+T_{\mathrm{readback}}}.
\]

Those formulae are **proposed benchmark definitions**, not fitted results. No numerical speedup is reported because no benchmark was run.

## Decision memo and delivered artefacts

The technical decision is **retain architecture, benchmark before adoption**.

**wgpu/WGSL remains the preferred primary path** because it fits the checked-in GPU facade and CPU-authoritative ownership model while maintaining a native Rust host API and broader portability. Current wgpu 30 should be evaluated rather than automatically merged because of its MSRV jump and current Metal-specific open issues. fileciteturn14file0L2-L2 fileciteturn6file0L2-L2

**MLX is the strongest secondary comparator**, particularly for dense chained transforms, reductions and candidate-score graphs that can remain resident. Its unified-memory model is genuinely relevant on Apple Silicon, but it does not turn arbitrary Rust host buffers into zero-copy MLX arrays automatically. It also introduces C/C++/FFI/runtime ownership rather than preserving a wholly Rust-native implementation. citeturn17search0turn17search1

**CubeCL is a later architectural option**, not the immediate answer. It may become attractive if CareOps accumulates many custom compute kernels and wants one Rust kernel language across Metal/other backends; current MSRV/runtime maturity and subgroup-control limitations make that extra layer unjustified before workload evidence exists. fileciteturn16file0L2-L6 fileciteturn35file0L3-L7

**Direct `objc2-metal` should be a profiling-triggered escape hatch**, not the default. Its MSRV fits the current Kairos floor, but the price is Apple-only resource/synchronisation management plus Metal shader/tooling ownership. citeturn18search2 The older `metal-rs` route should not be started anew because upstream explicitly deprecates it. citeturn18search5

## Conflicts, unresolved questions and priority evidence actions

The first conflict is **current dependency versus current Kairos MSRV**. Current wgpu 30.0.1 requires Rust 1.93 while the inspected Kairos workspace declares 1.76; mlx-rs and CubeCL likewise exceed that floor. fileciteturn6file0L2-L2 fileciteturn24file0L2-L6 fileciteturn16file0L2-L6 The correct response is not to freeze automatically on an old dependency and not to upgrade silently: benchmark current technology in isolation, then make MSRV change a separately reviewed architectural decision.

The second conflict is **unified memory versus API-level copies**. Apple Silicon and MLX genuinely offer shared physical memory, but wgpu `Queue::write_buffer` still stages/copies caller data and MLX CPU-origin array creation can copy into MLX storage. citeturn16search4turn16search7turn17search1 Consequently, claims such as “Metal has no transfer cost” or “MLX is automatically zero-copy from Kairos” are unsupported.

The third conflict is **deterministic simulation versus floating accelerator semantics**. Exact event/RNG/order contracts are compatible with device acceleration only when numeric device results are reconciled behind that boundary. WGSL’s floating specification and MLX’s precision/device rules do not justify requiring portable float bit identity. citeturn16search16turn17search4turn17search5

The highest-priority missing evidence is therefore not another GPU framework survey. It is the **actual ED numeric workload envelope**: array dimensions, number of independent calibration candidates, number of W1/KS evaluations per calibration iteration, whether samples are already sorted/reused, how many transforms can stay resident, and the fraction of run time currently consumed by those numeric stages. Those values are currently **unknown**, because the generic-ED attachments were unavailable.

The next evidence action is a frozen CPU fixture and profile from the generic/public-data ED path. It should establish **observed** batch-size distributions and current multicore timings before any hardware speedup threshold is set. Only then can the synthetic N grid be mapped to a real scenario range and a production break-even criterion be defined.
