# Queue/preemption reference semantics and test cases

## Scope, evidence boundary and research method

**Research date:** 27 September 2026, Australia/Brisbane.

This review is deliberately bounded to queueing, allocation, preemption and event-collision semantics for the proposed CareOps Sim queue layer. It does not treat later surgery, birthing, outpatient, waitlist, whole-hospital or whole-health modelling as in scope.

A material evidence limitation affects the conclusions: **the detailed CareOps Q specification/plan named in the research prompt was not available through the conversation attachments, and searches of the connected Drive/Linear sources for the distinctive terms `Suspend`, `Abort`, `Restart`, `atomic bundles`, `deadline`, `grant` and `preemption` did not locate an identifiable copy.** Consequently, the only project-intent facts attributed to CareOps are those explicitly supplied in the prompt: one resource and one capacity unit per work item, proposed `Suspend`/`Abort`/`Restart`, and atomic bundles deferred. All finer semantics below are therefore either source-backed facts about Kairos/SimPy or clearly marked **[policy] proposed for review**, not assertions about an unavailable Q spec.

## What Kairos actually implements in the inspected snapshot

The current Kairos scheduler is much firmer evidence than the queue proposal. Its `QueueEntry::cmp` reverses Rust `BinaryHeap` comparison so dispatch is ordered by **simulation time ascending, then numeric priority ascending, then monotonically assigned sequence ascending [observed]**. `schedule()` assigns both an `EventId` and sequence; `step()` removes the live event from `pending`, advances the authoritative clock to its event time and dispatches it. `cancel(EventId)` removes the ID from `pending`; cancelled heap entries are then lazily discarded by `prune_dead_entries()`. fileciteturn6file0L1-L7 The repository's own tests explicitly check time→priority→sequence dispatch and that cancellation removes an event without reordering the remaining live events. fileciteturn7file0L1-L7

That ordering should therefore be treated as an architectural invariant rather than redesigned for the queue layer:

\[
\boxed{(\text{time},\ \text{event priority},\ \text{sequence})}
\]

with smaller time first, smaller numeric priority first, then smaller sequence first. **[observed]** fileciteturn6file0L1-L7

The current `kairo-ecs-des::Resource`, by contrast, is a small preview primitive rather than the proposed queue/preemption system. It stores `capacity`, `available` and a `VecDeque<EntityId>`. A request consumes exactly one available slot; if none is available, the entity is appended to the back of the deque. `release()` either pops the front waiter—effectively transferring the slot—or increments `available` up to `capacity`. There is no request token, owner set, request priority, deadline, preemption policy, `Suspend`, `Abort`, `Restart`, queued-request cancellation, runtime capacity mutator or atomic bundle API in that inspected file. **[observed]** fileciteturn8file0L1-L7 The Flow specification establishes the intended common DES/ABM kernel but does not add these queue semantics. fileciteturn9file0L1-L7

This distinction matters. The proposal must **not** be reverse-imputed into current behaviour.

There is also a useful counterexample in the present preview primitive. Because `release()` takes no ownership/request token, a caller can invoke it without proving which active allocation is being relinquished. With capacity one and multiple queued entities, repeated erroneous `release()` calls can successively pop waiters. That follows directly from the inspected implementation and means the existing `Resource` cannot itself serve as a reference oracle for ownership-safe preemption. **[observed/inference from source]** fileciteturn8file0L1-L7

## SimPy reference semantics and relevant DES literature

SimPy is useful as a comparison implementation, but it should not become CareOps's implicit specification.

A SimPy `Resource` represents capacity slots through explicit `Request` events; a request triggers when access is granted, and the resource retains request events for its current users. A `PriorityResource` orders pending requests by ascending numeric priority. A `PriorityRequest` documents its sorting key as **priority, request time, then preemption flag**: lower numeric priority is more important, earlier request time is more important, and a preempting request is more important at the final component. citeturn28view0

A `PreemptiveResource` can displace an existing user. The displaced process receives an `Interrupt` whose cause is a `Preempted` value containing the preempting process, the time the victim began using the resource (`usage_since`), and the resource lost. SimPy therefore supplies enough information to calculate elapsed work, but it does **not** dictate whether model work should resume, restart or terminate after the interruption. citeturn28view0 Its current Machine Shop example demonstrates exactly this division: preemption/interrupt mechanics come from the framework, whereas continuation of interrupted work is model logic. citeturn27search2

Two SimPy details deserve particular attention for conformance tests:

* A waiting resource event can be interrupted and then either yielded again to keep waiting or explicitly `cancel()`led; context-manager resource events automatically cancel a still-pending request on exceptional exit. citeturn28view0turn28view1
* `release()` is deliberately permissive: the documentation states that releasing a resource succeeds immediately even if the process was not actually using it. This is a SimPy behaviour, not a desirable CareOps ownership invariant to copy automatically. citeturn28view0turn28view1

SimPy's simulation clock is deterministic rather than concurrent at one instant: events sharing a simulation time are processed serially in event-queue order, and ordinary same-time ties preserve scheduling order. citeturn28view2 This is conceptually compatible with Kairos's stronger explicit `(time, priority, sequence)` contract, but it does **not** create a general semantic rule such as “deadline always beats grant” or “completion always beats preemption”. Those are model/event-priority choices.

SimPy also has condition events including `AnyOf` and `AllOf`; those conditions wait for constituent events. They do not turn independent resource requests into an atomic multi-resource transaction. citeturn28view3 Thus `AllOf([r1.request(), r2.request()])` must not be used as evidence that SimPy supplies atomic resource bundles: either individual request may acquire its resource while the other remains pending.

The older queueing literature is useful principally for terminology. Chang's 1965 *Preemptive Priority Queues* distinguishes **preemptive-resume** from preemptive-repeat disciplines, including repeat-identical and repeat-different variants; the publisher record is *Operations Research* 13(5), 820–827, DOI `10.1287/opre.13.5.820`. citeturn29search0 Gaver's 1962 *A Waiting Line with Interrupted Service, Including Priorities*, *JRSS Series B* 24(1), 73–90, DOI `10.1111/j.2517-6161.1962.tb00438.x`, provides an earlier analytical treatment of single-server interrupted service. citeturn29search1turn29search3 These are analytical queueing models, not empirical healthcare samples, so their **sample size/population is N/A** for CareOps calibration.

That literature supports one important modelling conclusion: “what happens to partially completed service after interruption” is not incidental implementation detail. It is part of the queue discipline and must be explicit. That is why `Suspend`, `Abort` and `Restart` should have separate conformance tests rather than being collapsed into a generic “preempted” state.

## Hand-worked event timelines and counterexamples

All times, work quantities and priorities in this section are **[synthetic]**. They are exact test fixtures, not observed ED data. Notification names such as `Granted`, `Preempted` and `DeadlineExpired` are **[policy] logical assertions**, not claims that those Rust enum variants already exist.

### Suspend as preemptive-resume

`TC-SUSPEND-001` uses capacity `1 [synthetic]`. A starts at `t=0`, has full required work `10`, queue priority `5`; B arrives at `t=4`, has priority `1` and work `3`.

| Time | Event | Allocation after event | Hand calculation | Expected logical notification |
|---|---|---|---|---|
| `0 [synthetic]` | A granted | A | remaining = 10 | `Granted(A)` |
| `4 [synthetic]` | B preempts A | B | A elapsed = `4−0=4`; A remaining = `10−4=6` | `Preempted(A, Suspend, elapsed=4, remaining=6)` |
| `7 [synthetic]` | B completes | A resumes | B elapsed = 3; A still has 6 | `Completed(B)`, `Granted(A, remaining=6)` |
| `13 [synthetic]` | A completes | none | resumed A elapsed = 6; total useful A work = 10 | `Completed(A)` |

This is the proposed **preemptive-resume** interpretation, not a statement of existing implementation. SimPy provides the corresponding interruption timing information but leaves the work arithmetic to the model. citeturn28view0turn27search2

### Abort and Restart must not collapse into Suspend

For the same A/B setup, `TC-ABORT-001 [synthetic]` gives A four units of completed elapsed time before interruption. Under the proposed Abort oracle, A becomes terminal at `t=4`; its `6` units of unperformed work may be reported for audit but are never requeued. B therefore runs `t=4…7`, with no later A allocation. **[policy]**

For `TC-RESTART-001 [synthetic]`, A again loses four units at `t=4`, but its next attempt resets to full required work `10`:

\[
\text{elapsed discarded}=4,\qquad
\text{new remaining}=10
\]

B runs `4…7`; A's new attempt runs `7…17`. The proposed oracle increments an attempt generation so the old completion associated with A's first attempt cannot mutate the restarted attempt. **[policy]**

This specific “reuse the original 10 rather than draw again” choice is **not yet established CareOps behaviour**. It is a candidate mapping to classical preemptive-repeat-identical semantics and has the desirable property of not changing the RNG consumption contract merely because a preemption occurred. The alternative—repeat-different/re-sample—must be explicit if intended. Chang's literature makes the distinction between resume and repeat disciplines material rather than cosmetic. citeturn29search0

### Deadline and grant at exactly the same tick

The unavailable Q spec prevents declaring one side the winner. The safest conformance suite therefore contains the two scheduler-valid branches rather than smuggling in a new tie rule.

Assume A releases at `t=5 [synthetic]` and waiting B has a deadline at `t=5 [synthetic]`.

**`TC-DEADLINE-GRANT-A` — release/grant event precedes deadline by the existing Kairos event key**

1. A completion/release executes.
2. B becomes granted.
3. B's deadline event executes later and finds B no longer waiting.
4. Expected assertion: `DeadlineHandlerIgnoredAsStale(B)`.

**`TC-DEADLINE-GRANT-B` — deadline precedes release by the existing Kairos event key**

1. Deadline removes/cancels B from waiting eligibility.
2. A completes/releases.
3. No grant may be issued to B.
4. Expected assertion: `DeadlineExpired(B)` and `NoGrantToCancelledB`.

Both branches preserve Kairos's existing event ordering. fileciteturn6file0L1-L7 The eventual Q contract should determine which event-kind priority/sequence is generated, rather than introducing a queue subsystem with a competing hidden notion of simultaneity.

### Completion and preemption at exactly the same tick

`TC-COMP-PREEMPT-A/B` is the more important collision counterexample.

Let A start at `t=0 [synthetic]` with required work `5`; a higher-priority B request is processed at `t=5`.

If **A completion executes first**, then:

\[
elapsed_A=5,\qquad remaining_A=0
\]

A transitions to completed, releases the slot, and B receives a normal grant. There should be **no `Preempted(A)` notification**.

If **B's preempt request executes first**, naïve arithmetic says the victim has:

\[
remaining_A=\max(0,5-(5-0))=0.
\]

A system that nevertheless transitions A to “Suspended with zero remaining” and then processes the old completion can emit contradictory state transitions or a double completion. **[synthetic counterexample]**

The reviewed Q spec therefore needs one of two things: either its existing event priorities make completion precede preemption at the boundary, or it defines how a zero-remaining victim is normalised. What it should **not** do is rely on unspecified container iteration or thread timing; Kairos already supplies deterministic event order. fileciteturn6file0L1-L7

### Cancellation and stale completion

`TC-STALE-COMPLETE-001 [synthetic]` tests a classic stale-event failure:

* A starts at `t=0`, required work `10`; completion `E1` is scheduled for `t=10`.
* At `t=4`, A is suspended: elapsed `4`, remaining `6`.
* `E1` is cancelled. The observed Kairos core contract says successful cancellation removes the event from the pending set, so it must not dispatch at `t=10`. fileciteturn6file0L1-L7
* A resumes at `t=7`; replacement completion `E2` is scheduled for `t=13`.
* At `t=10`, assertion: `E1` produces no state mutation.
* At `t=13`, `E2` completes the active attempt.

The **[policy]** additional generation check is deliberate defence in depth: `(work_id, attempt_generation)` on a completion should still match authoritative work state before mutation. That protects future implementations where cancellation may race with dispatch or where distributed/parallel backends have a different physical cancellation mechanism without changing logical semantics.

### Capacity shrink and resource-bundle counterexamples

`TC-CAP-DOWN-001 [synthetic]` starts with capacity `2`, active A and B, queued C, then changes capacity to `1` at `t=3`. The proposed non-preemptive shrink oracle is:

| Time | Active after event | Expected result |
|---|---|---|
| `3 [synthetic]` | A, B | temporary active count 2 > new capacity 1; **no forced preemption** |
| `5 [synthetic]` | B | A completes; active count = capacity, so C remains queued |
| `7 [synthetic]` | C | B completes; active count falls below capacity, so C is granted |

This is **[policy]**, because neither the inspected Kairos primitive nor the standard documented SimPy Resource supplies the requested runtime resizing contract. fileciteturn8file0L1-L7 citeturn28view0

The bundle counterexample `TC-BUNDLE-DEFER-001 [synthetic]` is intentionally simple:

1. capacity(R1)=capacity(R2)=1;
2. A acquires R1 and waits for R2;
3. B acquires R2 and waits for R1;
4. neither can progress.

That is a valid outcome for independent resource requests and shows why waiting for multiple request events is not the same thing as atomic acquisition. SimPy's condition-event machinery does not change the underlying independent grants. citeturn28view3 Under the supplied CareOps scope, the correct reference outcome is therefore **“atomic bundles unsupported/deferred” [elicited]**, not an invented partial implementation.

## Conflicts, unresolved questions and evidence priorities

### Conflicts and cautions

**The largest conflict is evidentiary rather than algorithmic:** the requested detailed CareOps Q spec was unavailable. Therefore none of the proposed tie, preemption, restart or resize choices should be promoted from **[policy]** to “project contract” until checked against an immutable copy of that specification.

**Current Kairos is not the proposal.** The core scheduler has a clear deterministic contract, but the current DES `Resource` is a simple FIFO, single-slot-per-request primitive without request ownership tokens, work-progress state or preemption modes. fileciteturn6file0L1-L7 fileciteturn8file0L1-L7 Tests written against the research proposal must therefore not be reported as existing Kairos capability.

**SimPy is a comparison point, not a compatibility target.** In particular, SimPy deliberately allows permissive release behaviour and leaves interrupted-work semantics to model code. citeturn28view0turn28view1 A stricter ECS contract can legitimately diverge.

**`Restart` is under-specified.** Classical preemptive-repeat policy can mean repeat-identical or repeat-different; those alternatives have different stochastic and RNG consequences. citeturn29search0 The reference package uses repeat-identical only as an explicit **[policy] proposed default**, not as a discovered requirement.

**Runtime capacity zero is unresolved.** SimPy's ordinary `Resource` requires positive capacity, while the inspected Kairos constructor accepts a `u64` and therefore can be constructed with zero in source as written. citeturn28view1 fileciteturn8file0L1-L7 Whether zero means “resource offline”, is invalid, or is permitted only through a future capacity schedule needs an explicit CareOps decision.

### Prioritised evidence-acquisition actions

**Highest priority — recover and freeze the actual Q spec/plan.** Record its immutable revision/hash and extract, verbatim at field/section level, the intended queue key, queue-priority direction, deadline/grant rule, completion/preemption rule, cancellation state machine, exact definitions of Suspend/Abort/Restart, capacity-change semantics and event/notification vocabulary. Until then, `CM-DEADLINE-GRANT-001`, `CM-COMP-PREEMPT-001`, `CM-RESTART-001` and `CM-CAPACITY-001` remain unresolved policy candidates.

**Highest priority — record the event-kind priorities that realise those choices.** The goal should be to express collision precedence through the already-authoritative Kairos `(time, priority, sequence)` mechanism, not add another ordering subsystem. The paired collision cases in `test_cases.json` can then collapse from parameterised alternatives into single expected oracles. fileciteturn6file0L1-L7

**High priority — obtain an immutable raw SimPy 4.1.2 source snapshot.** Verify `resource.py`, `base.py`, `core.py` and `events.py` at tag 4.1.2/commit `f4381649…`, record full commit SHA and line locations, and run minimal reference scripts for equal-priority/same-time queue ties, mixed priority/preemption, pending cancellation and same-tick condition-event races. The official 4.1.2 documentation is adequate for the present semantic comparison, but the research request specifically asked for primary source and the raw source could not be inspected through the available fetch path. citeturn27search22turn28view0

**High priority — resolve Restart sampling and stale-event identity together.** Decide explicitly whether a restart reuses the original sampled full work requirement or draws a fresh requirement, and define the attempt/generation identity carried by completion events. This is needed to make deterministic seed consumption and stale-event rejection independently testable.

**Next priority — freeze capacity-change invariants.** Decide whether capacity decrease is non-preemptive drain or an explicit source of preemption, whether capacity zero is legal, and which queued items receive newly created capacity. These should be policy-level conformance tests before any implementation claim.

**Deferred — atomic bundles.** The current scope already says bundles are deferred. The appropriate present test is therefore negative: no API or example should claim that independent requests, `AllOf`-style waiting or sequential acquisition provides atomic multi-resource allocation. Any bundle protocol belongs in a separately reviewed phase rather than being smuggled into this queue contract.
